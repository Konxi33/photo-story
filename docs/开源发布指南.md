# 开源发布指南（给仓库主人的操作说明）

这份文档记录：开源前做了什么清理、仓库怎么组织、发版怎么做。

## 一、开源前已经清理的东西

| 项 | 处理 |
|---|---|
| **内置 API Key** | `src/config/app.ts` 的 `DEFAULT_AI_API_KEY` 已清空为 `''`；`.devtools/fix-aikey.cjs` 里的 Key 也已抹掉。现在读 Key 的顺序是 **设置页/配置文件 > 环境变量 `OPENAI_API_KEY`**，仓库里不含任何密钥。 |
| 用户照片与运行时数据 | `data/`、`安装包/`、`.shots/`、`.devtools/`、`*.docx`、`*.pptx` 全部写进 `.gitignore`，不进仓库。 |
| 旧版本的安装包 | **不要上传**。0.5.5 及更早的 exe 里编译进了旧的内置 Key，传上去等于公开它。需要发安装包时，只用清理后的源码重新构建（0.5.6 起）。 |
| README 截图 | `docs/screenshots/` 里是软件真实界面截图（含示例照片）。不想公开这些照片的话，删掉这 6 张并改 README 的图片引用即可。 |

> 建议：如果之前的安装包曾经发给别人，去 <https://platform.deepseek.com> 把那个 Key 吊销重发一个。

## 二、仓库结构

```
src/            应用代码（Next.js App Router）
electron/       桌面端主进程 / preload
scripts/        构建与发版脚本
build/          安装器脚本与图标（installer.nsh、icon.ico）
docs/           截图与文档
更新日志_*.md    每个版本一份中文更新日志（README 与 Release 说明都引它）
项目现状.md      工程现状：目录、数据模型、踩坑清单
设计决策与历史档案.md  为什么这么做（架构决策记录）
```

## 三、第一次推送到 GitHub

```bash
git remote add origin https://github.com/<你的用户名>/photo-story.git
git push -u origin main
```

推之前确认：`git status` 干净、`.env.local` 与 `data/` 没有被跟踪。

## 四、密码 / Key 放哪里（硬规矩）

真实 Key **永远不进仓库、不进安装包**，只放在这台电脑的运行时配置里：

```
%APPDATA%\photo-story\data\ai-config.json
```

那个目录在仓库外，安装包也不会打包它 —— 所以「装到别人电脑上仍然需要自己填 Key」是设计如此，不是缺陷。

三道保险已经自动化：

1. `src/config/app.ts` 的 `DEFAULT_AI_API_KEY` 固定为空字符串（装了包的人自己填）。
2. `npm run check:secrets` 扫描全部受 git 控制的文件，发现 `sk-xxxx` 真实 Key 就报错；**CI 每次 push 都会跑这一步**（`.github/workflows/check.yml`）。
3. `npm run release` = 先跑密钥检查再构建，顺序上就不可能把带 Key 的包做出来。

本机写 Key 用：

```bash
# 把 Key 放进 .devtools/local-api-key.txt（该目录已被 .gitignore 忽略）
node .devtools/set-local-key.cjs
```

## 五、发版（每次版本更新都要做，一个版本一个 Release）

固定流程，五步，别跳：

```bash
# 1. 改版本号（package.json 与 src/config/app.ts 的 APP_VERSION 两处都会改）
node .devtools/bump-version.cjs 0.5.7

# 2. 写这一版的中文更新日志（Release 说明就是它）
#    更新日志_0.5.7.md，同时在 src/config/changelogs.ts 顶部加一条（应用内「更新日志」页要用）

# 3. 类型检查 + 密钥检查 + 构建安装包（release = check:secrets + electron:build）
npm run typecheck
npm run release

# 4. 建 Release 并挂安装包（附件用 ASCII 名，中文名会被 gh 吃掉）
cp "安装包/0.5.7/照片故事-0.5.7-安装版.exe" /tmp/PhotoStory-0.5.7-setup.exe
gh release create v0.5.7 --repo Konxi33/photo-story --target main \
  --title "0.5.7 · <这一版的一句话>" --notes-file 更新日志_0.5.7.md
gh release upload v0.5.7 /tmp/PhotoStory-0.5.7-setup.exe --repo Konxi33/photo-story --clobber

# 5. 推源码
git add -A && git -c http.sslVerify=false commit -m "release: 0.5.7"
git -c http.sslVerify=false push
```

## 六、构建

```bash
npm install
npm run dev            # 开发
npm run typecheck      # 类型检查（CI 会跑）
npm run lint           # ESLint（CI 会跑，0 error）
npm run check:secrets  # 密钥检查（CI 会跑）
npm run electron:build # 出 Windows 安装包
npm run release        # 密钥检查 + 出安装包（发版用这个）
```

## 八、这台机器上的坑（本机推代码前必看）

1. **这台机器原来没有 git**：用的是便携版 `C:\tools\PortableGit`，GitHub CLI 在 `C:\tools\bin\gh.exe`。新开一个 PowerShell 要先加 PATH：
   ```powershell
   $env:Path = "C:\tools\bin;C:\tools\PortableGit\bin;" + $env:Path
   ```
2. **`git push` 会因证书吊销检查失败**（`CRYPT_E_NO_REVOCATION_CHECK`，本机 TLS 被中间设备接管）。解决办法是推送时关掉校验：
   ```powershell
   git -c http.sslVerify=false push
   ```
3. **附件名别用中文**：`gh release upload` 经过 PowerShell 会把中文吃掉（`照片故事-0.5.6-安装版.exe` 变成 `-0.5.6-.exe`）。发版时统一用 ASCII 名，如 `PhotoStory-0.5.6-setup.exe`。
4. **PowerShell 5.1 读无 BOM 的 UTF-8 脚本会按 GBK 解析**（中文变乱码、直接语法错误）。写 `.ps1` 之后要补 BOM：
   ```powershell
   $p='脚本.ps1'; $t=[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8); [IO.File]::WriteAllText($p,$t,(New-Object Text.UTF8Encoding($true)))
   ```
5. **Node 的 `fetch` 在这台机器上连不上 GitHub**（同样因为 TLS 中间设备），所以发版脚本走 `gh`（Go 自带证书链）。仓库里的 `scripts/publish-releases.mjs` 在正常网络环境可用，本机请用 `gh release create`。
